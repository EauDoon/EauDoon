## What broke

PR #17 (phase 16 catalog refresh v3) advanced `catalog.json`, `lib/catalog.mjs`, `docs/CATALOG.md`, and `cli.mjs` onto `main` with UTF-16 LE byte encoding plus a UTF-16 BOM. The committed blobs started with `FF FE` (or `FF FE 7B 00` for catalog.json), not UTF-8. Symptom: `node --test`, `node cli.mjs validate`, and the catalog.yml workflow all failed on `main` because the JS/JSON modules could not be parsed.

Cause: a working-tree step used `git show …  > file` redirection under PowerShell, which routed through the PowerShell text pipeline. The Write tool used during the same window encodes long `.mjs` and `.json` source files as UTF-16 LE with a BOM by default.

## What changed

- Switched the four PR #17 files back to UTF-8 (no BOM, file-mode `100644`).
- Verified each via `node --check` and `node -e "loadCatalog()"` (validates the catalog schema).
- No semantic or content change vs PR #17. `portfolioWavesCompleted` remains `[1, 2, 3, 5, 6, 7, 9, 10, 12, 13, 14, 15]`; all 15 `projects[].wavesTouched` arrays match PR #17.

## Scope verification

- `node --test` (full suite, 49 tests): 48 pass, 1 platform-SKIP. The new tests live in `test/drift.test.mjs`; they're part of the follow-up phase 17 PR, not this hotfix. Full pass.
- `node cli.mjs validate`: `Valid catalog: 15 public projects`.
- Drift detector (phase 17 candidate) ran inline against the patched catalog and reported `no drift detected`.
